# Canonical drainage geometry (M3a groundwork)

## Confirmed target

The user clarified that Genesis targets an **infinite, non-repeating world with fully deterministic generation independent of request order**. There is no finite-map outer coast, wrapping planet, or viewport-defined outlet in the intended production model. The old external JavaScript prototype is unavailable and is not a development dependency. Visual assessment uses images generated by the code itself.

The current ±2^40 coordinate guard is an implementation/numeric support limit, not a world-design boundary or a place to discharge rivers. A computer cannot literally address infinitely many coordinates; within the supported range, a seed, complete parameter set, version, and world coordinate must specify exactly one result. Expanding numeric support later must not introduce a physical edge.

The finite `/hydrology.html` tool is intentionally a different experiment. Its edges affect both `edges` and `connectedWater` policies. Border-following routes in it are real boundary artifacts, not an infinite-world solution. Those results are never imported into the production core.

## Implemented production-core primitives

`BoundaryPorts` identifies a face by the exact tuple `(level, axis, i, j)`. Vertical faces lie at `x = i * spacing`, horizontal faces at `z = j * spacing`. North/east/south/west views from adjacent cells resolve to the same tuple. A hash is used for placement, never as a supposedly collision-free identity.

At level L, spacing is `coarseSpacing * 2^L`. Levels 0..20 are supported for this geometry primitive. This maximum does **not** declare hierarchy roots, cap river length, or prove eventual drainage. A port is placed within the face's central half using a two-block stride (odd offsets for standard slider-step spacings); v2 additionally skips any offset divisible by the finest base spacing, covering arbitrary custom spacings too. The central-half restriction is a structural corner-exclusion bound, not a terrain tuning knob.

An inherited coarse port lies in exactly one finer face. `childFace(port, finerLevel)` locates that face without changing the port's original identity or coordinates. Callers must carry the original commitment: **hashing the child face independently creates another port and is not refinement**. This supplies a stable crossing primitive, not the entire child-routing algorithm or permission to open other parent-boundary crossings.

`CoarseChannels` consumes only registered `coarseFlowDirection` values. Each cell connects its center hub to its outgoing crossing and any incoming crossings. Both sides of a crossed edge use the same port. Straight segments stay inside their owning cell; incoming and outgoing branches join at the same hub. This makes a connected geometric realization of the existing resolved coarse graph.

Two new fields appear in the main viewer's top bar:

| Field | Meaning |
| --- | --- |
| `coarseChannelDistance` | Floored integer Euclidean distance to the guide segments, capped at `coarseSpacing/4` |
| `drainagePortDistance` | Floored integer Euclidean distance to active shared crossing points, with the same cap |

The fixed 3×3 world-cell halo is sufficient for these capped distances: a farther cell cannot contain a segment within the cap. No requested viewport boundary, width, height, or pixel spacing enters the calculation. Segment projection and squared distances use integer arithmetic; with the level-zero geometry and maximum base spacing 16384, the products fit signed long. The distance implementation is compared to a larger-support BigInteger reference.

Memoization retains at most 512 immutable cell descriptions per generator. Crossings are returned defensively; synchronized access and eviction do not alter values. Shared-edge ownership, central-half support, cache sizes, and direction codes are documented algorithm/infrastructure constants in the lint allowlist. No new terrain tuning parameter is introduced.

The initial version was `genesis-m3a-v1`; `genesis-m3a-v2` fixes child-corner exclusion for arbitrary custom spacings. All 160 default field PNG baselines are unchanged. The geometry lives in the Java 8 core and has no dependency on the finite reference, browser, or Minecraft. A separate [conditioned-refinement kernel](Conditioned-Refinement.md) now consumes inherited ports and budgets without claiming global root generation.

## Deliberate limitations

- This consumes M2a's bounded nearest-sea-anchor graph, which can return unresolved and does not distinguish globally connected ocean from enclosed sea-level depressions. Missing routes stay absent; the numeric support edge does not invent ports to the outside.
- The hub of a coarse sea-anchor cell need not itself lie below sea level. Guide endings are not exact shoreline mouths. Guide segments are not conditioned terrain, and may cross uphill relief.
- These are **guides, not rivers**: no contributing area, rainfall, channel width, erosion, lake level, channel-bed profile, or complete coarse-to-fine cascade is claimed. Their angular or parallel appearance reflects the current coarse graph and straight-segment realization.
- Stable inherited port positions are only part of refinement. Child routing still needs exact boundary-transfer ownership, flux disaggregation, terminal handling, and containment between inherited ports.
- No bounded local algorithm can find an ocean in an intentionally all-land input. A complete model must construct reachable terminal commitments, explicitly support endorheic basins, or constrain such configurations. It must not disguise an unresolved case as a canvas-edge outlet.

## Executable checks and visual evidence

`genesis.ps1 test` now includes shared-face identity from both sides, negative/extreme seeds and coordinates, inherited fine-face containment, exact seam connectivity, defensive copies, a BigInteger distance reference, 5×5 versus 3×3 support, arbitrary-origin overlapping crops, common-point zoom checks, shuffled requests, cache eviction, concurrent requests, and existing 64×64-chunk cold/cached determinism over all 20 fields.

It also generates these actual Java-rendered images under `build/gallery/`:

- `canonical-seam-audit.png`: one 512² request beside four freshly constructed generators' 256² tiles requested in order 3,0,2,1. The images must match at every pixel before annotation. White dashed lines only mark the tile cuts.
- `canonical-guides-elevation.png`: the same guide/port geometry over macro elevation for qualitative inspection. Relief hillshade uses display-neighbor samples, so the exact stitching gate uses the pointwise land/sea backdrop instead.

Both images were inspected directly. Guides cross tile cuts unchanged; the straight/parallel coarse morphology remains plainly visible and is not represented as finished drainage. Renderer stroke thickness changes for legibility at different sample spacings; core positions and distances do not. This is code-image QA, not a claim of browser gesture testing.
